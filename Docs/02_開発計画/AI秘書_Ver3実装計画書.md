# AI秘書エージェント Ver3.0 実装計画書
## テーマ: "L0 First" - 圧倒的「秘書体験」の最速検証

### 1. 開発戦略 (Top-Down Approach)
コスト最適化（アーカイブ/ベクトル検索）よりも、**「体験の質」と「有用性」の検証を最優先**とする。
Gemini 2.0 Flash / Pro のロングコンテキスト性能（1M-2M tokens）を最大限活用し、**「直近のデータをすべてコンテキストに載せる」** アプローチを採用する。

*   **基本方針**: 
    1.  **保存**: ログはこれまで通り Firestore / Local に保存。
    2.  **想起**: 検索（RAG）は使わず、**直近3〜7日間の全ログ（PC操作、カレンダー、メール等）を生のまま** プロンプトに含める。
    3.  **検証**: これにより「AIがすべてを知っている状態」を作り出し、ユーザーが「これは便利だ」と感じるかをテストする。コスト削減はVer4以降で実施。

### 2. 実装機能 (Feature Scopes)

#### Phase 3.1: "Deep Memory" (全知の秘書)
過去の文脈を完全に理解したブリーフィング即時生成。
*   **Context Loader**:
    *   起動時および1時間ごとに、過去7日間の作業ログ・カレンダー・（可能なら）メール/チャット履歴を全取得。
    *   トークン圧縮（要約）などは**あえて行わない**。
*   **Executive Briefing**:
    *   プロンプト: 「あなたはCEOを20年支えた秘書」のPersonaを適用。
    *   出力: 「至急 (Do)」「準備 (Schedule)」「効率化 (Delegate)」等への構造化。

#### Phase 3.2: "Smart Tensai" (空気を読む割り込み)
ユーザーの集中を阻害しない、高度な割り込み制御の実装。
*   **Focus Sensing (Python/Node)**:
    *   キーボード打鍵速度 (KPM) とマウス移動距離の監視。
    *   集中スコア ($S_f$) のリアルタイム算出。
*   **Interruption Manager**:
    *   **Gatekeeper**: Geminiからの通知リクエストを一度保留する中間層。
    *   **Rule**: 
        *   $S_f > Threshold$ (集中時): 通知をキューに積んで「待機」。
        *   $S_f < Threshold$ (休憩/遷移時): 待機していた通知をまとめて「提示」。
        *   会議中（カレンダー/Web会議プロセス検知）: 完全ミュート。

#### Phase 3.3: "Hyper-Link" (外部脳との接続)
*   **Outlook/Linked-In Integration**:
    *   会議参加者の情報をWeb/SNSから取得し、人物プロファイルを補完。
    *   「誰と会うのか」「過去何をしたか」をブリーフィングに統合。

### 3. 技術スタック & アーキテクチャ

*   **Frontend**: React + Electron (既存)
*   **Sensing**: 
    *   **Python (`pynput`)** サイドカー構成を採用（※ユーザー推奨）。
    *   理由: 入力フックの実装が容易で、データ分析ライブラリ（pandas等）との親和性が高いため。
    *   構成: Electron (Main) <--> Proccess Spawn <--> Python Script
*   **AI Model**: 
    *   **Gemini 1.5 Pro / 2.0 Flash** (Context: ~2M tokens)

### 5. 既知のリスクと対策
*   **APIコスト**: 
    *   トークン量が膨大になるため、従量課金が高額になる可能性。
    *   対策: 開発中はデータを「直近1日」に制限し、ここぞという時だけフルコンテキストにするトグルを用意する。
*   **パッケージング (EXE化)**:
    *   Python環境の同梱が必要になり、インストーラーサイズが肥大化する。
    *   対策: ポータブル版Python (Embeddable Package) を同梱するか、PyInstallerでexe化して同梱する。
