#11）に関する包括的な調査結果、技術的要因の特定、およびその解決策を提示するものである。ユーザーが直面している「アクセス権限が切れている」という現象は、フロントエンドの認証フロー、Google OAuth 2.0の仕様、およびOS固有の暗号化ストレージの挙動が複雑に絡み合った結果であり、単一のコード修正に留まらないアーキテクチャレベルでの再設計が必要であることが判明した。認証アーキテクチャの現状と脆弱性の特定現在の実装における認証フローは、Firebase JS SDKのsignInWithPopupメソッドに依存しており、ログイン成功時に返されるオブジェクトから非公開プロパティである_tokenResponseを介してリフレッシュトークンを抽出する手法をとっている 。この設計は、開発段階では機能するものの、本番環境における堅牢性を著しく欠いており、Issue #11の根本的な原因の一つとなっている。Firebase JS SDKにおける非公開API依存のリスクFirebase JS SDK v9以降、SDKはモジュール式の設計に変更され、内部実装の隠蔽が進んでいる。現在利用されているresult._tokenResponse.refreshTokenというプロパティは、SDKの公式ドキュメントに記載されていない内部的な実装詳細である 。Firebase SDKのバージョンアップや、Firebaseがバックエンドで使用しているGoogle Identity PlatformのAPI仕様変更に伴い、このプロパティが突然undefinedになる、あるいは構造が変化するリスクは極めて高い 。実際、Firebase SDKはGoogle Calendarなどのサードパーティ製APIのトークン管理を肩代わりするようには設計されていない 。Firebaseの主な役割は「Firebaseユーザー」としての認証を管理することであり、Googleのアクセストークンやリフレッシュトークンは、あくまで認証の副産物として一時的に渡されるものに過ぎない。これを永続化の基盤として利用することは、SDKの設計意図から逸脱しており、更新フローの不安定化を招いている。Google OAuth 'consent'が適切に指定されていない可能性がある。これにより、初回ログイン時にはリフレッシュトークンが取得できたとしても、二回目以降のログインではGoogleが既存の権限付与を検出し、リフレッシュトークンを省略してアクセストークンのみを返す挙動となる 。以下の表は、Google DPAPIの永続性分析ElectronのsafeStorage APIは、OS固有の暗号化メカニズムを利用してデータを保護する。Windows環境においては、MicrosoftのData Protection API (DPAPI) がその下層を支えている 。DPAPIの仕組みと復号失敗のメカニズムDPAPIは、ユーザーのログオン資格情報（パスワードのハッシュ値）から派生したマスターキーを使用してデータを暗号化する 。この仕組みは非常に強力なセキュリティを提供する一方で、以下の要因によって暗号化されたデータの「鍵」が失われる、あるいは無効化されるリスクを孕んでいる。Windows Updateによる影響: 大規模なOSのアップデートにより、LSASS（Local Security Authority Subsystem Service）が管理するキーチェーンの整合性が損なわれる事例が報告されている 。これにより、アップデート前に暗号化されたデータが、アップデート後に復号不能となる。パスワード変更と同期不全: Windowsのログインパスワードが変更された際、DPAPIのマスターキーは通常自動的に更新されるが、エンタープライズ環境やドメイン参加環境、あるいは特殊なログイン管理ソフトを使用している場合、この同期が失敗し、旧パスワードで暗号化されたデータにアクセスできなくなることがある 。プロファイルのリセット: Windowsのユーザープロファイルが破損、あるいはリセットされた場合、SID（Security Identifier）は同一であっても暗号化キーが消失するため、safeStorageに保存されたデータは永久に失われる 。Electronにおける復号エラーのハンドリングsafeStorage.decryptStringは、復号に失敗した場合にエラーをスローする仕様となっている 。現状のChatService.tsにおけるリトライロジックでは、エラーハンドリングが不十分である可能性が高く、復号エラーが発生した際にトークンがundefinedとして扱われ、そのまま401エラーとして処理されている 。Signal DesktopやVSCodiumなどの著名なElectronアプリにおいても、DPAPIの不全に起因する「amnesic（健忘症的）」な挙動、すなわち再起動のたびにログインを求められる現象が数多く報告されており、これはIssue #11と同一の構造的問題である 。Firebase v10における堅牢なトークン取得の代替案非公開APIである_tokenResponseに依存せず、公式にサポートされた方法でリフレッシュトークンを確保するためには、アーキテクチャの転換が必要である。Google Identity Platform Blocking Functionsの活用2023年以降、Firebase Authenticationのアップグレード版である「Identity Platform」において提供されている「Blocking Functions（ブロッキング関数）」を利用することが、最も堅牢な解決策である 。この手法では、認証プロセスが完了する直前にサーバーサイド（Cloud \Delta T$$ここで $\Delta T$ はネットワーク遅延や処理時間を考慮したバッファであり、一般的には 300秒（5分）程度が推奨される。現状の実装のように、401エラー（事後検知）を待ってからリフレッシュを行うのではなく、トークンの有効期限を管理し、期限が切れる前にバックグラウンドで更新を試みることで、AIの回答中断を防ぐことができる 。401エラーハンドリングの高度化401エラーが発生した際のフローにおいて、原因が「トークンの期限切れ」なのか「権限の剥奪（Revoke）」なのかを判別する必要がある。401エラーの種別判定方法推奨されるアクションアクセストークン期限切れリフレッシュトークンが存在し、有効refreshGoogleToken を実行しリトライリフレッシュトークン無効リフレッシュ試行時に invalid_grant が返るユーザーに再ログイン（再認可）を促すストレージ復号失敗safeStorage.decryptString がエラーを投げるローカルデータを破棄し、再ログインを促すネットワークエラーHTTPステータス 5xx またはタイムアウト指数バックオフによるリトライ特に、safeStorageの復号失敗は致命的であり、単なる「権限切れ」として扱うのではなく、「ストレージの不整合」として検知し、保存されている暗号化バイナリを削除した上で、クリーンな状態で再認証フローへ誘導する設計が求められる 。永続性向上のための設計変更案Issue #11の解決に向け、以下の3つのフェーズに分けた改善策を提案する。フェーズ1：認証パラメータの修正（即時実施）App.tsxにおいて、GoogleAuthProviderの設定にaccess_type: 'offline'とprompt: 'consent'を追加する。これにより、既存ユーザーが再ログインした際にリフレッシュトークンが確実に再発行されるようになる 。また、_tokenResponseが取得できなかった場合には、サイレントに無視するのではなく、明確なエラー状態としてユーザーに通知し、再試行を促すように変更する。フェーズ2：サーバーサイドキャプチャへの移行（短・中期）Firebase Identity Platformにアップグレードし、Blocking Functionsを導入する。クライアント側のwindow.ipcRenderer.saveSecureTokenによるローカル保存への依存を減らし、重要なリフレッシュトークンはFirestore等の安全なバックエンドで管理する 。これにより、Windows Update等のローカル環境の変化による認証情報の喪失を完全に回避できる。フェーズ3：Electronストレージの耐障害性強化ローカルにトークンを保存し続ける必要がある場合（オフライン対応等）、safeStorageの呼び出しタイミングをapp.whenReady()以降に厳密に制御する 。さらに、復号失敗を検知した際には、ユーザーに対し「セキュリティ設定の変更が検知されました」等の適切なメッセージを表示し、再ログインを誘導する。総括Issue #11「カレンダー自動更新失敗」は、Firebase SDKの非公開プロパティへの依存、Google OAuthのトークン発行ルールの誤解、およびWindows DPAPIの不安定さが重なった、複合的な障害である。本報告書で示した通り、_tokenResponseによるトークン取得を廃止し、Google Identity PlatformのBlocking Functionsを利用したサーバーサイド管理へと移行することが、将来にわたる最も堅牢な解決策となる。また、フロントエンドでの認証パラメータ設定を最適化することで、既存ユーザーの認証継続性を担保できる。これらの修正を段階的に実施することで、AIによるスケジュール確認機能の信頼性は飛躍的に向上し、ユーザー体験の劇的な改善が見込まれる。本報告書内での主要な知見のまとめ（テクニカルマトリクス）カテゴリ課題点推奨される解決策SDK利用非公開プロパティ _tokenResponse の不安定性Firebase Identity Platform Blocking Functions への移行OAuth仕様リフレッシュトークンの再発行制限access_type: 'offline' と prompt: 'consent' の付与暗号化ストレージWindows DPAPI の更新による復号失敗復号エラーのキャッチとクリーンな再認証プロセスの実装更新ロジック事後的な401ハンドリングの限界有効期限に基づいたプロアクティブなトークン更新
