Electron環境におけるFirebase JS SDKを用いたGoogle OAuthリフレッシュトークン取得の技術的限界と建築学的解決策ElectronとReact、そしてFirebase JS SDK v10を組み合わせたモダンなデスクトップアプリケーション開発において、Google Calendar APIのような外部APIとの持続的な連携は一般的な要件である。しかし、GoogleAuthProviderを使用したsignInWithPopupフローにおいて、開発者が期待するoauthRefreshTokenがクライアントサイドのレスポンスから欠落するという現象は、多くの技術者を悩ませる深刻な障壁となっている。この現象は単なる実装ミスやSDKのバグではなく、GoogleのIdentity PlatformおよびFirebase SDKの設計思想、さらにはOAuth 2.0のセキュリティ仕様の進化に伴う必然的な結果である。本報告書では、この問題の根本原因を深く掘り下げ、Electron特有の環境制約を考慮した上で、現実的かつ堅牢な解決策を提示する。OAuth 2.0における「公開クライアント」とセキュリティ・パラダイムの変遷Google OAuthリフレッシュトークンがクライアントサイドで取得できない最大の理由は、ElectronアプリケーションがOAuth 2.0の仕様において「公開クライアント（Public Client）」として分類される点にある。公開クライアントとは、アプリケーション内にclient_secret（クライアント機密情報）を安全に保持できない環境を指す 。ブラウザベースのSPAや、ソースコードが容易に解析可能なElectronのレンダラープロセスは、本質的にこの範疇に含まれる。歴史的に、ブラウザベースのアプリケーションでは「インプリシット・フロー（Implicit Flow）」が利用されてきたが、このフローではセキュリティ上の理由からリフレッシュトークンは発行されない。現代ではPKCE（Proof Key for Code Exchange）を用いた「認可コードフロー」への移行が推奨されているが、Googleの認可サーバーは依然として、ブラウザコンテキストからのリクエストに対してリフレッシュトークンを直接返却することに極めて慎重である 。Firebase JS SDK v10は、Identity Platformの上に構築された高レベルな抽象化レイヤーであり、その主な目的は「ユーザーの認証（Identity）」の管理にある。Google Calendar APIの操作に必要な「認可（Authorization）」の管理、特にリフレッシュトークンのような長期間有効な資格情報の配布は、SDKのクライアントサイドにおける責務から意図的に除外されている 。Firebase JS SDK v8からv10へのアーキテクチャの変化Firebase SDKのバージョン進化に伴い、認証情報のカプセル化はより厳格化された。以下の表は、各世代におけるトークンの取り扱いの差異を示している。SDK バージョントークンアクセスの可用性アーキテクチャの特徴セキュリティ上の位置付けv8 (Namespaced)_tokenResponseに比較的容易にアクセス可能であったモノリシックな構造セキュリティ境界が不明瞭v9 (Modular)UserCredentialから認可情報がカプセル化され始めた関数型、ツリーシェイキング対応内部プロパティへの依存を非推奨化 v10 (Current)_tokenResponseは非公開プロパティとして厳格に管理される高度なモジュール化クライアントサイドでのトークン露出を最小限に抑制開発者がresult._tokenResponseを参照してリフレッシュトークンを探す行為は、現在のSDK設計においては「非推奨な内部構造への依存」とみなされる。Firebaseは、開発者がプロバイダー固有の機密情報に直接触れることなく、Firebase IDトークンを通じてエコシステムを利用することを想定しているのである 。Electron環境特有の制約とプロトコルの干渉Electronアプリケーションは、ChromiumのレンダラープロセスとNode.jsのメインプロセスという二重の実行環境を持つ。この構造がOAuthのフロー、特にリダイレクト処理において特有の問題を引き起こす。リダイレクトURIとプロトコルの制限OAuth 2.0では、認可サーバーが認可コードを返却するための「リダイレクトURI」が厳格に検証される。Electronでは多くの場合、アプリケーションのコードはfile://プロトコルで読み込まれるが、Google OAuthはセキュリティ上の理由からfile://プロトコルをリダイレクトURIとして一切認めていない 。この制限を回避するために、Firebase SDKはポップアップウィンドウ内で一時的なプロキシページ（__/__/auth/handler）を使用し、Firebaseのホスティングドメインを仲介役として利用する。この仲介プロセスにおいて、Googleから返却された生のOAuthレスポンスはFirebaseのバックエンドで処理され、クライアントには「Firebaseのセッション確立に必要な情報」だけがフィルタリングされて返却される。このフィルタリングプロセスこそが、oauthRefreshTokenが消える物理的なポイントである 。LocalhostとループバックIPの挙動開発環境においてhttp://localhostを使用する場合、OSのホスト解決やネットワーク・アイソレーションの影響を受ける可能性がある。RFC 8252（Native Apps向けのOAuth 2.0ベストプラクティス）では、localhostというホスト名ではなく、127.0.0.1というループバックIPリテラルを使用することが強く推奨されている 。これは、DNSの改ざんや他のローカルプロセスによる傍受のリスクを低減するためである。しかし、Firebase JS SDKを使用している限り、リダイレクトはSDK内部で制御されるため、開発者がリダイレクトURIの挙動を完全に制御することは困難である。クライアントサイドのみでの取得不可能性に関する技術的裏付け調査依頼事項の核心である「クライアントサイド（Electron）のみで確実にリフレッシュトークンを取得できるか」という問いに対し、現在のGoogleおよびFirebaseの仕様に基づけば「不可能である、あるいは極めて非推奨なハックが必要である」という回答が導き出される。Googleの認可サーバーは、リフレッシュトークンの発行条件として以下の要素を厳格に要求する。access_type: 'offline'の指定 。ユーザーによる明示的な同意（prompt: 'consent'） 。機密クライアント（Confidential Client）であることの証明、あるいは適切に構成されたネイティブアプリ用クライアント。Firebase JS SDKのsignInWithPopupは、これら全ての条件をバックエンドでラップしており、返却されるUserCredentialオブジェクトの公開インターフェースには、プロバイダー（Google）のリフレッシュトークンを含まない。_tokenResponseに存在するrefreshTokenは、前述の通りFirebase Authのセッション更新用であり、Google APIのエンドポイント（https://oauth2.googleapis.com/token）に送信しても、発行元が異なるためinvalid_grantとなるのは仕様通りの挙動である 。Identity Platformブロッキング関数によるサーバーサイド・キャプチャクライアントサイドでの取得が封じられている現状において、Googleリフレッシュトークンを安全かつ確実に取得する唯一の「公式な」道筋は、Firebase AuthenticationをIdentity Platformにアップグレードし、Cloud Functionsの「ブロッキング関数（Blocking Functions）」を活用することである 。ブロッキング関数のメカニズムブロッキング関数は、ユーザーが認証を完了した後、Firebase Authがクライアントにトークンを返却する直前のタイミングで実行されるサーバーサイドのトリガーである 。このタイミングでは、Googleから返却された生の資格情報（認可コードから交換された直後のトークンセット）がサーバーサイドのメモリ上に存在しており、これをインターセプトすることが可能である 。ブロッキング関数を使用する際のシステム構成要素を以下の表にまとめる。構成要素役割必須設定Identity PlatformFirebase Authの拡張機能プロジェクト設定での有効化が必要 実装パターン：トークンの安全な永続化ブロッキング関数内でリフレッシュトークンを取得した場合、それをクライアントに直接返却するのではなく、サーバーサイド（FirestoreやSecret Manager）に保存し、必要な時だけサーバーサイドから利用、あるいはセキュアな経路でクライアントに提供するのがベストプラクティスである。以下に、Node.jsを用いた実装の論理構成を示す。JavaScript// Firebase Functions (v2) を使用したブロッキング関数の例
import { beforeUserSignedIn } from "firebase-functions/v2/identity";
import { getFirestore } from "firebase-admin/firestore";

export const onBeforeSignIn = beforeUserSignedIn(async (event) => {
  const credential = event.credential;
  
  // Googleプロバイダーかつリフレッシュトークンが存在するか確認
  if (credential && credential.providerId === 'google.com') {
    const googleRefreshToken = credential.refreshToken;
    const uid = event.data.uid;

    if (googleRefreshToken) {
      const db = getFirestore();
      // Firestoreのセキュリティルールで保護された場所に保存
      await db.collection('secure_tokens').doc(uid).set({
        googleRefreshToken: googleRefreshToken,
        updatedAt: new Date().toISOString()
      }, { merge: true });
    }
  }
  
  // 認証フローを続行
  return;
});
この方法の決定的な利点は、リフレッシュトークンが一度も「信頼できないクライアント（Electronのレンダラー）」を通過しないことである。これにより、トークン漏洩のリスクを劇的に低減できる。ElectronメインプロセスにおけるネイティブOAuthフローの構築もし、インフラ構造上の制約でIdentity PlatformやCloud Functionsを利用できない場合、あるいはオフライン環境での動作を重視する場合、Firebase SDKに頼らず、Electronのメインプロセスで独自のOAuthフローを構築するという代替案がある。これは、Electronを純粋な「ネイティブアプリケーション」として扱う手法である。Google Auth Libraryを用いたメインプロセス実装Electronのレンダラープロセス（React）ではなく、Node.js環境であるメインプロセスでgoogle-auth-libraryを使用することで、より低レベルな制御が可能になる 。認可URLの生成: access_type: 'offline'、prompt: 'consent'、およびresponse_type: 'code'を指定して認可URLを生成する。システムブラウザの利用: Electron内のポップアップではなく、OS既定のブラウザ（shell.openExternal）でURLを開く。これは「このブラウザは安全ではありません」という警告を回避するためにも有効である 。ループバックサーバーの起動: メインプロセスで一時的なHTTPサーバー（127.0.0.1:port）を立ち上げ、リダイレクトされる認可コードを待ち受ける 。トークン交換: 取得した認可コードを、メインプロセスから直接Googleのトークンエンドポイントへ送信し、アクセストークンとリフレッシュトークンを取得する。Firebaseへのサインイン: 取得したGoogle IDトークンを使用して、FirebaseのsignInWithCredentialを呼び出す。これにより、Google API用のトークンとFirebaseのセッションを同時に確立できる 。このアーキテクチャでは、リフレッシュトークンはメインプロセスで保持されるため、セキュアなストレージへの保存が容易になる。Windows環境におけるトークンのセキュアな保管：safeStorage APIリフレッシュトークンをクライアントサイド（Electron）で保持する場合、その保管方法が次なる課題となる。Windows環境においては、Electronが提供するsafeStorage APIを利用することが、OSレベルのセキュリティを享受するための標準的な手段である 。DPAPIの仕組みと信頼性safeStorageは、WindowsのData Protection API (DPAPI) をバックエンドで使用している 。これは、ユーザーのログイン認証情報から派生した暗号化鍵を用いてデータを保護する仕組みであり、以下の特性を持つ。特性内容セキュリティ上の意義ユーザー固有同一マシンの他のユーザーは復号できないマルチユーザー環境での保護アプリケーション境界他のアプリケーションからのアクセスは制限される（OSの設定に依存）マルウェアによる搾取防止マスターキーの保護LSASSプロセスによって管理されるメモリ上からの直接取得を困難にするしかし、DPAPIには「Windowsパスワードが管理者によって強制リセットされた場合、既存の暗号化データにアクセスできなくなる」という脆弱性が存在する 。このような事態に備え、アプリケーションは復号に失敗した際の再ログインフローを適切に設計しておく必要がある 。safeStorageの実装例トークンを保存する際は、文字列をバッファとして暗号化し、それをelectron-storeやSQLiteなどの永続化層に格納する。JavaScript// メインプロセスでのトークン保存処理
const { safeStorage } = require('electron');
const Store = require('electron-store');
const store = new Store();

function saveToken(token) {
  if (safeStorage.isEncryptionAvailable()) {
    const encrypted = safeStorage.encryptString(token);
    store.set('google_refresh_token', encrypted.toString('latin1'));
  }
}

function loadToken() {
  const encrypted = store.get('google_refresh_token');
  if (encrypted) {
    return safeStorage.decryptString(Buffer.from(encrypted, 'latin1'));
  }
  return null;
}
