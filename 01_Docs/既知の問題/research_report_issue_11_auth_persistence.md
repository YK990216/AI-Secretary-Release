# 技術調査報告書: Google Calendar API 認証永続化の課題 (Issue #11)

**対象バージョン**: v0.6.5
**作成日**: 2026/02/18
**ステータス**: 調査完了 (v0.7.0にて恒久対応予定)

---

## 1. 概要
本報告書は、Firebase JS SDK v10およびElectronフレームワークを採用したデスクトップアプリケーションにおいて発生した、Google Calendar APIの自動更新失敗（Issue #11）に関する調査結果と解決策をまとめたものである。

**現象**:
アプリ起動から1時間経過後、カレンダーの自動更新が失敗し、認証エラー（アクセス権限切れ）が発生する。

## 2. 原因分析

### 2.1. 認証アーキテクチャの不整合
*   **現状の実装**: Webアプリ向けの `Firebase JS SDK` をElectron（デスクトップアプリ）で使用している。
*   **問題**: Google OAuth 2.0 の仕様上、ブラウザベースのフロー（User-Agent Flow）ではセキュリティの観点から **リフレッシュトークン（長期的なアクセス権）の発行が制限** される場合がある。

### 2.2. 非公開APIへの依存
*   これまで利用していた `_tokenResponse.oauthRefreshToken` プロパティはFirebase SDKの非公開APIであり、信頼性が低い。
*   特定の条件下（2回目以降のログイン等）で、このプロパティが欠落することが判明した。

## 3. 推奨される解決策 (v0.7.0 Roadmap)

根本解決には、Webアプリとしての振る舞いではなく、**ネイティブデスクトップアプリ** としての正しい認証フローへの移行が必要である。

### Phase 1: ネイティブアプリフローへの移行 (推奨)
RFC 8252 (OAuth 2.0 for Native Apps) に準拠した実装を行う。

1.  **Main Processでの認証**:
    *   認証処理をRenderer (UI) から Main Process (Node.js) へ移動する。
    *   `google-auth-library` を使用し、堅牢なトークン管理を行う。
2.  **ループバックIP認証**:
    *   ローカルサーバー (`http://127.0.0.1:xxxx`) を一時的に立ち上げ、システムブラウザで安全にログインを行う。
3.  **トークンの安全な保存**:
    *   取得したリフレッシュトークンは、Electronの `safeStorage` APIを用いてOSレベルで暗号化して保存する。

---

## 4. 暫定対応 (v0.6.5)
v0.7.0でのアーキテクチャ刷新までの間、以下の暫定対応を実施した。

*   **エラーの抑制**: トークン更新失敗時にアプリを停止させるのではなく、警告ログの出力に留める（ユーザー操作を阻害しない）。
*   **影響**: 1時間以上経過した場合、カレンダー同期が停止する可能性があるが、アプリの再起動で復旧する。
